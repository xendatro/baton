# Baton REST API

The REST API lives under `/api`, speaks JSON, and is what the web app uses. Scripts can use it too,
with `Authorization: Bearer bat_…`. The zod schemas in `shared/schemas/*.ts` define every request
and response below. If this file and a schema disagree, the schema is right; fix this file.

## Conventions

- **Auth**: the web app uses the Better Auth session cookie; scripts send `Authorization: Bearer bat_…`.
  Requests that change data and use a cookie must send an `Origin` (or `Referer`) that matches
  `BASE_URL`. Accounts with an unverified email or no username get `403 email_not_verified` /
  `403 username_required` from every endpoint except `/api/auth/*`, `GET /api/me` and `GET /api/config`.
  Every `/api` endpoint except `/api/auth/*` and `GET /api/config` needs a signed-in user: anonymous
  requests get `401 unauthorized` before any body is read or validated (unknown paths included).
- **Body size**: JSON bodies are capped at 2 MB (above the largest text field, a 200,000-character
  README) and Better Auth's `/api/auth/*` bodies at 64 KB; larger bodies get `413 payload_too_large`
  as soon as `Content-Length` (or the streamed body) passes the cap. Uploads (`POST /api/attachments`,
  `POST /api/me/avatar`) and `/mcp` have their own limits.
- **Errors**: every response that isn't 2xx looks like `{ "error": { "code", "message", "details"? } }`
  (`apiErrorSchema`). Codes: `unauthorized` 401, `forbidden` 403, `not_found` 404,
  `validation_failed` 400 (`details.issues: [{ path, message }]`), `conflict` 409,
  `rate_limited` 429, `payload_too_large` 413, `email_not_verified` 403, `username_required` 403,
  `agents_paused` 423 (an agent member's write while it, its team or its project is paused; reads
  still work), `internal` 500. If a resource belongs to a team the caller isn't a member of, the API returns
  `404`, never `403`.
- **Ids** are ULIDs. **Timestamps** are ISO 8601 strings (`…At`). **Due dates** are `YYYY-MM-DD`.
- **Pagination**: `?cursor&limit` (limit 1–100, default 50) → `{ items, nextCursor }`. `nextCursor`
  is null on the last page. Treat cursors as opaque.
- **Deletes** return `{ ok: true }` (`okResponseSchema`).
- **`202 Accepted`** `{ pendingApproval: true, requestId, message }` (`pendingApprovalResponseSchema`):
  an agent's destructive action now waits for its owner's sign-off and nothing changed yet (see
  Agent action requests). Only API keys ever get it.
- **Live updates**: after a change commits, the server sends a hint on `GET /api/events` (see below).
- **Rate limits** (token buckets, `429 rate_limited` with `Retry-After`): `POST /api/auth/*` 10/min per
  IP (Better Auth adds stricter per-path limits: 3 sign-in/sign-up attempts per 10 s, one code email per
  60 s); REST writes 120/min per user; uploads 30/min per user; MCP 300/min per key.
- **API keys** can call every REST endpoint except `/api/me/api-keys` and `/api/me/agent` (web
  session only). A key belongs to a person, but a request with it acts as that person's **agent
  member** (`ethan-ai`, "Ethan AI"; agents A, docs/design/agents-and-pipelines.md §1): everything it
  writes is authored by the agent "via" the key, `GET /api/me` answers with the agent, its
  permissions in a team are its own roles intersected with its owner's (never the owner), and its
  inbox is empty (agents get no notifications). Destructive actions may wait for the owner's
  sign-off (`202`, see Agent action requests below); owner-only actions (delete, restore or transfer
  a team) are never taken by agents directly: their owner's agent can only ask for them. Membership is the person's: creating a team, accepting an invite or
  leaving through a key does it for the key's owner (their agent follows); a team created through a
  key gives the agent its Admin role. The profile, avatar and security log through a key are the
  owner's. A person and their agent count as one author (either can edit, delete or restore what
  the other wrote, and use the other's pending uploads). The agent's writes answer `423
agents_paused` while its owner paused it.

`ApiKey` = `{ id, name, prefix, lastUsedAt, expiresAt, revokedAt, createdAt }`.

Project order (BAT#27): `PUT /api/me/teams/:teamId/projects/order` `ReorderMyProjectsInput`
`{ projectIds }` (1–1000 distinct ids of the team's projects you can see, top first) arranges that
team's projects in your sidebar and answers the new `MeResponse`, whose `projects` then come in
your order; projects left out (created meanwhile, say) and never-arranged ones follow, by name.
Projects only move within their team: another team's, a deleted or a hidden project is `400`; not
a member of the team: `404`. It replaces your saved order of that team, emits `me.updated` and
writes no activity (personal, like the team order).

Notifications (list, unread count, `me.unreadNotifications` and MCP `list_notifications`) leave out
those about an issue, task, reply or project README that is in Trash, directly or through its issue,
task or project; they come back if it is restored. Editing an item's title or text updates the
`title` of its notifications and the `snippet` of those quoting the text (mentions, assignments,
replies).

`POST /api/notifications/read` takes exactly one of `ids`, `all: true` or `item` (BAT-15):
`item: { type: 'task'|'issue', id }` marks the caller's unread notifications about that task or
issue and about its replies (the web app sends it when the item's page shows its thread, and again
for notifications arriving while it is on screen in a visible tab; MCP `get_task`/`get_issue` never
mark anything read). Every mark-read sends the caller a personal `notification.read` live event per
affected project (`projectId`; with `item`, also `parentType`/`parentId` = the item), so their
other tabs refresh the inbox, the unread count and the item badges. `notification.created` events
carry the notification's `projectId` and, as `parentType`/`parentId`, the task or issue it is about
(a reply's item).

Reactions (BAT-14): `emoji` is exactly one emoji grapheme (skin tones, ZWJ sequences, flags and
keycaps included) of at most 32 UTF-8 bytes, else `400`. A target has at most 50 different emojis
(a new one beyond that is `409`). Tasks (`Task.reactions`), issues (`Issue.reactions`) and replies
(`Reply.reactions`) carry their reactions, one entry per emoji in order of its first reaction,
reactors oldest first. Missing, deleted and other teams' targets are `404`. Reactions notify nobody
and write no activity; each change emits `reaction.changed`.

### Uploads and downloads

- `POST /api/attachments` takes `multipart/form-data` with the file in `file` (a body that isn't valid
  multipart is `400 validation_failed`). Files above `MAX_UPLOAD_MB` or beyond the team's
  `TEAM_STORAGE_QUOTA_MB` get `413 payload_too_large`. The stored
  type is sniffed from the content; the filename is sanitized. Without a parent the upload is
  `pending`: only the uploader can see it, and it must be claimed within 24 h by passing its id in
  `attachmentIds` (replies) or the feature's equivalent, or by linking it (`/api/attachments/<id>/…`)
  from the saved text (issue and task bodies, READMEs, replies and reply edits), or it is purged.
  Pending uploads need a permission that writes content (`REPLY`, `CREATE_ISSUES`, `CREATE_TASKS`,
  `UPDATE_TASKS`, `EDIT_ANY_CONTENT` or `MANAGE_PROJECTS`; otherwise `403`), and one member's pending
  uploads in a team may total at most a tenth of `TEAM_STORAGE_QUOTA_MB` (at least `MAX_UPLOAD_MB`;
  beyond that `413`). A parent that is missing, deleted or in another team is `404`. Uploading straight to a
  parent needs edit rights on it (author / `EDIT_ANY_CONTENT`; tasks also `UPDATE_TASKS`; projects
  `MANAGE_PROJECTS`). `parentType: 'user_avatar'` is rejected here (account settings handle avatars).
- `GET /api/attachments/:id/:filename`: only PNG, JPEG, GIF and WebP whose bytes match are served
  `inline`; everything else, SVG and HTML included, is `attachment`. `Cache-Control: private,
max-age=31536000, immutable`, an `ETag` (`If-None-Match` → 304) and `X-Content-Type-Options: nosniff`.
  Scripts and agents download with `Authorization: Bearer bat_…` like any other endpoint (a plain
  GET without a session cookie or key is `401`).

### `GET /api/events` (Server-Sent Events)

- Each message is a default (`message`) event whose `data` is one JSON `LiveEvent` (`shared/events.ts`):
  `{ type, teamId, projectId?, entityType, entityId, parentType?, parentId?, actorId, userId?, at }`.
- The stream carries events for every team the user belongs to, plus their personal events
  (`notification.created`, `notification.read`, `me.updated`, `agent_job.changed`, delivered only
  to `userId`).
- `presence.changed` (entity: the team) says members of the team came online or went offline; the
  server sends at most one per team every 3 s. `agent_job.changed` (personal, to an agent's owner)
  says the agent's jobs or listener sessions changed.
- An open stream, or a pending long-poll (and the 60 s after it), makes a person online
  (`GET /api/teams/:teamId/presence`). Streams opened with an API key don't count: agents are
  online through their listener (`start_listener`).
  (`notification.created`, `notification.read`, `me.updated`, `agent_action.changed`, delivered only
  to `userId`).
- The server sends a `: ping` comment every 25 s and a `retry: 3000` hint.
- Events only say what changed. They carry no data: clients refetch (`web/lib/live.ts` maps each
  type to the TanStack Query keys it invalidates).
- `parentType`/`parentId` name the parent item for `reply.*` and `attachment.changed`, and the
  entity the row is about for `activity.created`.
- `reaction.changed` names the task, issue or reply in `entityType`/`entityId`; for a reply,
  `parentType`/`parentId` name its task or issue.
- `typing` (chat): `actorId` is typing in the issue or task named by `entityType`/`entityId`.
  Ephemeral: nothing to refetch; clients show "X is typing…" for 5 s after the last one, and drop
  it when a `reply.created` from that person arrives.
- Right after the `retry` hint the server sends one `ready` event (`event: ready`, `data: {}`). The
  web app waits up to 8 s after opening the stream for it; some proxies (Cloudflare quick tunnels)
  pass the headers through but hold the body back, and then it long-polls instead (below).

### `GET /api/events/poll` (long-poll fallback)

- The same events as the stream, as ordinary JSON responses: `{ events, cursor, reset }`.
- Without `cursor` it answers at once with `events: []` and a cursor to start from. With one it
  answers as soon as there are events after it, or with `events: []` after 25 s. Pass the returned
  `cursor` to the next poll.
- `reset: true` means events may have been missed (the server restarted, or more than the last
  1000 events went by): refetch everything. Cursors are opaque.

### Agent jobs and the listener (MCP, docs/design/agents-and-pipelines.md §4)

Agent members have no inbox. What would notify one becomes an `agent_job`: `mention` (its
username in a reply, task description or issue body), `assigned` (a task assigned to it
directly), `thread_reply` (someone else replied on a task or issue it authored, replied on or is
assigned to), `pool` / `approval` (pipelines), `action_result` (sign-off) and `catch_up` (its
owner asked for a private summary of a chat; see below). One pending job per
agent, kind and item: later triggers update it (the newest reply is the trigger; earlier ones are
listed in `earlierReplyIds`; a mention and a thread reply on the same item are one `mention` job).
No jobs are queued for paused agents or agents that can't see the project.

- `start_listener { projects: [KEY | team/KEY | id] (1–50, required), timeoutSeconds = 50 (≤ 110),
sessionId? }` → `{ sessionId, projects: [{ id, ref, name }], skipped: [{ ref, reason }], jobs }`.
  Registers or refreshes the listener session (pass `sessionId` back) for those projects only,
  then claims up to 10 pending jobs of those projects atomically, or waits for the first. Each job:
  `{ jobId, kind, status, closing, createdAt, project: { id, ref, name }, target: { type, id, ref,
title, url, status }, trigger: { replyId, author: { username, name, kind }, body, closing, url,
createdAt } | null, earlierReplyIds, stageInstructions, payload, instructions }`. Projects where
  agents are paused are `skipped`; `agents_paused` when the agent or all the projects are paused.
- Claimed jobs stay with their session until `complete_job { jobId, agreeDone? }` or
  `release_job { jobId }` (back to pending). No leases: only when a session is not seen for 90 s
  (it is seen at every listener call and while it waits) are its claimed jobs put back (checked
  every 15 s and at every listener call).
- `list_jobs { status?, limit = 20 }` → `{ jobs, pendingCount }`, newest first.
- Chat: a `mention` or `thread_reply` job on an item whose `conversationMode` is `chat` says so in
  its `instructions` (and the desktop brief's rules): answer briefly, like a chat message, with
  `add_reply { inReplyTo }` on the message that pinged it.
- `catch_up` (`POST /api/items/:type/:id/catch-up`): only ever for the requester's own agent, never
  waiting for an OK. It targets the range's newest message (`target.type` = `reply`, so a desktop
  runner working on the item doesn't merge it into that session); `payload` is `{ itemType, itemId,
range: { kind, count, fromReplyId, toReplyId } }`. The desktop brief contains the messages; a
  listener reads them with `list_replies`. The agent hands in markdown with
  `submit_catch_up { jobId, summary }`, which stores it in `catch_up_summary` for the owner only
  (shown in the chat's Catch up panel; `agent_job.changed` refreshes it) and completes the job. It
  never posts in the chat.
- Loop guard: a reply by an agent queues no `mention`/`thread_reply` jobs when the item's last 5
  replies are all by agents; the first time, a system activity row `<type>.agent_loop_guard` is
  recorded. A person's reply resets it.
- Done handshake: a job triggered by another agent's `closing` reply has `closing: true`;
  `complete_job { agreeDone: true }` (only on such jobs) records `<type>.agents_agreed_done` (meta
  `agents`, `with`) and stops jobs from agent replies on that item until a person replies.

### Automatic agents: the desktop app (BAT-24, docs/design/agents-and-pipelines.md §8)

Schemas in `shared/schemas/agentRunner.ts`, chain resolution in `shared/agentChains.ts`. Runner
endpoints need an API key (they act as the key owner's agent member); the owner endpoints under
`/api/me/agent/*` accept the web session or the owner's key.

- `POST /api/agent/runners { machineId, machineName, harnesses: [{ id, version }], projectIds }`
  → `RunnerState { runner: { id, machineId, machineName, harnesses, projectIds, running,
lastSeenAt, online }, paused, pausedReason, waitingCount }`. One runner per (agent, machine):
  re-registering updates it. Only projects the agent can see are kept. `GET /api/agent/runners`
  → `{ runners }` (the owner's).
- `POST /api/agent/runners/:runnerId/heartbeat { harnesses?, projectIds?, running, jobIds? }` →
  `RunnerState & { cancelledJobIds }` (send at least every 30 s; a runner not seen for 90 s is
  offline and its claimed jobs go back to the queue, like listener sessions). `jobIds` are the
  jobs running there; `cancelledJobIds` names those cancelled meanwhile (e.g. their task was
  deleted, BAT-33): the app kills their harness and releases them without holding them.
- `POST /api/agent/runners/:runnerId/jobs/next?wait=50` (≤ 110) → `{ jobs: AgentJobContext[] }`:
  claims up to 10 pending jobs of the runner's projects atomically, or waits for the first. Jobs
  waiting for the owner's OK are skipped. `agents_paused` while the agent is paused. Job contexts
  also carry `triggeredBy` (username) and `needsOk`.
- `GET /api/agent/jobs/:jobId/brief?runner=` → `{ jobId, kind, project, target, difficulty, chain:
[{ harness, model, effort }], chainSource, resume: { harness: sessionId }, prompt }`. The chain
  comes from the owner's mappings for the task's difficulty in the stage the job is for (BAT-28:
  `payload.statusId` when it names another stage the task has been in, else its current stage;
  the prompt's "Difficulty" line names the stage) (its level, else the closest mapped
  level below, then above, else the account default for a level of that name, else the default
  chain); `resume` lists the harness sessions of that task on the runner's machine. BAT#28: for
  `thread_reply` and `mention` jobs the harness that has been working on the item comes first —
  the one with the most recent stored session of that task on the runner's machine, else the
  harness of the agent's most recent write there (creating it or replying), from the write's
  agent name ("Claude" → `claude`, "Codex" → `codex`) — with its chain entry's model and effort
  (empty for its defaults when the chain lacks it) and the rest of the chain after it;
  `chainSource` then ends with "; <Harness> first: it has been working on this task".
- `PUT /api/agent/jobs/:jobId/session { runnerId, harness, sessionId, items? }` stores the harness
  session a task's job ran in (per agent, task, machine and harness). `items` (BAT#28, at most 50
  refs or ids): tasks the run created or replied in, read by the app from the harness's Baton
  tool calls; each gets the same session unless it already has one for that harness there
  (never replaced); refs the agent can't see and issues are skipped.
- `POST /api/agent/jobs/:jobId/complete { usage: JobUsage[], agreeDone?, deliveredTo?, outcome?,
error?, output? }` and `…/release { usage, hold?, outcome?, error?, output? }` complete or
  release the job (release of a finished job returns it unchanged). `deliveredTo` (BAT#31): the
  job's message went into the running session of that other job of the agent on the same runner;
  it is kept as `payload.deliveredTo`. Both record usage per harness run `{ harness, model,
reportedModel, effort, tokensIn, tokensOut, tokensCacheRead, tokensCacheWrite, tokensReasoning,
costUsd, durationMs, outcome: done | released | killed | out_of_usage | failed | permission_denied,
error }`. BAT#25: `tokensIn` is all input (cache reads and writes included), `tokensOut` all output
  (reasoning included), `reportedModel` the model the harness said it ran, `costUsd` 0 when it
  reported none; every new field has a default, so older apps still work. BAT#23: `outcome` (a
  usage outcome, or `no_harness | no_folder | error`; default: the last usage entry's), `error`
  (the last error line; 2 000 characters kept) and `output` (the output's tail: the last 200 lines
  and 64 000 characters are kept, longer input is cut, never rejected) are stored on the job.
  `hold: true` (a failed or killed run) puts a released job under Stopped runs. MCP
  `complete_job` / `release_job` take the same optional `usage`.
- Is your agent connected here? `GET /api/projects/:projectId/agent-connection?taskId=` (anyone
  who can see the project; the web session asks about the person's agent, a key about its own) →
  `{ agent: { id, username, name } | null, project: { id, ref, name, repoUrl }, paused,
pausedReason, pausedBy: owner | team | project | null, agentCanView, covered, runners: [{ id,
machineName, online, coversProject }], listening, pendingJobs, pendingJobsForTask?,
taskInvolvesAgent? }`. `covered`: an online runner has the project in its `projectIds` (a folder
  on that machine) or a live `start_listener` session listens to it; otherwise the agent's jobs
  there stay pending. `pendingJobs` counts the agent's pending jobs in the project (those waiting
  for the owner's OK included). With `taskId` (a task of the project, else 404):
  `pendingJobsForTask` (jobs about the task or a reply in its thread) and `taskInvolvesAgent` (the
  agent is assigned in the current stage, may claim it from the pool, matches the stage's hand-off
  or approvals rule, or has jobs there). The web shows "Your agent isn't connected … Connect now"
  from it; `agent_job.changed` (runners registering, listeners starting, jobs) refreshes it.
- Whose jobs run: `GET/PUT /api/me/agent/job-sources { mode: me | anyone | custom, rule }` (default
  `me`: jobs the owner or their agent caused; system jobs always run). Jobs caused by others get
  `needsOk: true`: runners skip them until `POST /api/me/agent/jobs/:jobId/approve` (Approve, or
  Retry for a stopped run); `…/dismiss` cancels (Decline, or Trash). Manual `start_listener`
  sessions still get every job.
- Jobs waiting on the owner (BAT#22, BAT#29): `GET /api/me/agent/waiting` → `{ jobs: [{ jobId,
kind, status, createdAt, triggeredBy, needsOk, project, target: { ref, title, url }, trigger:
{ body } | null, group: needs_ok | stopped | cleared, run: { outcome, error, harness, model,
endedAt, hasOutput } | null, clearedAt, clearedReason: finished | deleted | resolved | moved |
unassigned | null }] }`, oldest first. `needs_ok`: caused by someone outside the job sources;
  `stopped`: held by a runner after a failed or killed run; `cleared`: a held or waiting job whose
  item no longer needs it (its task entered a stage that doesn't block dependents or was deleted,
  its issue was resolved or deleted, the task left the stage the job was for, or an `assigned`
  job's agent isn't assigned to the current stage any more). Those are cancelled when the change
  happens (and by a 5-minute sweep), listed for 24 h, then no more. `GET
/api/me/agent/jobs/:jobId/output` → `{ jobId, run, output }`: the stored tail of the job's last
  run (the owner's jobs only, else 404); the full log stays on the computer.
- `GET /api/me/agent/model-failures` → `{ failures: [{ harness, model, error, at }] }` (BAT#23):
  per harness and chain model (canonical), the error of its latest run in 30 days when that run
  failed (out-of-usage and killed runs don't count); the chain editors show it as "Last run
  failed: …".
- Model mappings: `GET/PUT /api/me/agent/models { default: { chain, levels: { levelName: chain } },
projects: { projectId: { levels: { levelId: chain } } } }` (chains of up to 8 steps; project
  levels must be the project's; empty chains are dropped).
- Your settings for one project (BAT-29), for anyone who can see it (a key reads and writes its
  owner's): `GET /api/projects/:projectId/my-settings` → `{ projectId, notifications: { level:
all | mentions | none, kinds: { replies, roleMentions, issueStatus, stages } } | null,
agentNotifications: all | needs_me | none | null, models: { levels: { levelId: chain } },
defaults: { notifications, agentNotifications, models } }` (null = "Use my defaults").
  `PUT` the same path with any of `{ notifications?, agentNotifications?, models?: { levels } }`
  replaces those parts (null or an empty chain: back to the defaults) and returns the settings.
  `models` edits this project's entry of the model mappings above. Notifications about the
  project are filtered by the override: `mentions` keeps mentions and assignments, `none` keeps
  nothing, `all` drops the kinds switched off; agent sign-off requests always get through.
- `GET /api/me/agent/stats?days=30` → `{ days, totals, byDay, byHarness, byModel, byDifficulty,
byOutcome }`; each total is `{ jobs, tokensIn, tokensOut, tokensCacheRead, tokensCacheWrite,
tokensReasoning, costUsd, costEstimatedUsd, unpricedRuns, durationMs }` (BAT#25). `costUsd` is what
  the harnesses reported; runs without a reported cost are priced at API list prices
  (`shared/modelPrices.ts`, dated) into `costEstimatedUsd`, or counted in `unpricedRuns` when their
  model has no known price. `byModel` groups by harness and the model the harness reported (else
  the chain's) as a canonical id: trimmed, lower-case, without a provider prefix, a date or `[1m]`.
- `GET /api/teams/:teamId/presence` also lists online runners: `runners: [{ agentUserId,
machineName, running }]`. Projects have an optional `repoUrl` (`PATCH` the project).

### MCP (`/mcp`)

Streamable HTTP, stateless: `POST /mcp` with `Authorization: Bearer bat_…` (401 +
`WWW-Authenticate: Bearer` otherwise). `GET` and `DELETE` answer `405` (no sessions). Every write is
attributed to the key owner's agent member (`ethan-ai`) with `source: 'mcp'` and the key name;
non-read-only tools answer `agents_paused` while the agent is paused. `whoami` returns the agent
(`user`: `{ id, username, name, kind, mentionHandle }`), its `owner` and the key (`via`);
`list_notifications` is always empty for agents (with a `note` pointing at `start_listener` and
`pendingJobs`, the number of jobs waiting).
Core tools: `whoami`, `search`,
`list_notifications`, `mark_notifications_read`, `list_replies`, `add_reply`, `edit_reply`,
`delete_reply`, `upload_attachment`, `list_attachments`, `get_attachment`, `delete_attachment`,
`get_activity`, `subscribe`, `unsubscribe`, plus the documented additions `wait_for_mentions`
(deprecated), `add_reaction` and `remove_reaction`. Listener tools (documented additions, see
"Agent jobs" below): `start_listener`, `complete_job`, `release_job`, `list_jobs`,
`submit_catch_up`.

Conventions shared by every tool:

- Inputs are strict: an unknown or misspelled argument (top level or nested) is an error that names
  it, suggests the parameter it probably meant and lists the accepted ones (`Unknown parameter
"labels" (did you mean "label"?). Accepted: …`); the advertised JSON schemas carry
  `additionalProperties: false`.
- Task, issue, search and trash results carry team-qualified refs (`northwind/WEB-12`,
  `northwind/WEB#51`) and `teamSlug` where the entity has a team, so a ref an agent was given keeps
  resolving when another of its teams creates a project with the same key. Short refs are still
  accepted; an ambiguous one lists the qualified candidates (`northwind/WEB-1, side-quests/WEB-1`).
  App URLs (`…/t/team/p/KEY/tasks/12`) are accepted as refs too.
- Errors are `code: message`, followed by the error's details as JSON when they add something (e.g.
  `{"key":"WEB","suggestion":"WEB2"}`). Not-found messages name the failing ref and list the valid
  values (`Status not found: "Doing" in northwind/WEB. Statuses: Backlog, Todo, …`); a ref of the
  wrong kind (`WEB#9` passed as a task) is `validation_failed` saying so. Validation messages name
  the tool's parameters (`assignees`, `status`), not the REST fields.
- Every tool is annotated `openWorldHint: false`; read tools `readOnlyHint: true`; every other tool
  states `destructiveHint` (true only for deletions, removals, ownership transfer and unassigning
  roles) and `idempotentHint` where repeating the call changes nothing more.
- `list_replies` pages a thread (`limit`, `cursor`, `order` asc/desc → `{ item, total, nextCursor,
replies }`), flat, each reply with `parentReplyId` (the reply it answers; it may name a deleted
  reply); `get_task`/`get_issue` return `conversationMode` (`chat` or `forum`) and
  `create_task`/`create_issue` take `conversation` (`chat` by default); `add_reply` works the same
  in both modes and takes `inReplyTo` (a reply id of the same item) to answer a reply, and
  `get_task`/`get_issue` show `parentReplyId` on their latest replies; `get_activity` with `item` or `entityType` + `entityId` pages the history the same
  way. `add_reply` and `edit_reply` validate like REST (a whitespace-only body is `validation_failed`)
  and return absolute file URLs; `add_reply` takes `closing: true` ("no further discussion needed
  at this time", the agents' done handshake). `wait_for_mentions` (`{ timeoutSeconds = 50, max 110 }`,
  deprecated alias of `start_listener`) returns the replies that @mentioned the key's agent member
  (`@ethan-ai`) in any project it can see, each once per agent (they are marked done): at once
  when some are pending, else the first to arrive within the timeout (`{ deprecated, mentions: [{
item: { type, ref }, reply }] }`). A paused agent gets no jobs. `get_attachment` returns the text of any file up to 256 KB whose
  content is UTF-8 text (source files, diffs, logs), whatever its extension. For PNG, JPEG, GIF and
  WebP images it adds the picture as an MCP `image` content block after the JSON: as it is when it
  fits 1568 px on the long side and 1 MB, else scaled down (PNG kept when it fits, JPEG otherwise;
  animations keep their first frame). `image` in the JSON gives `{ mimeType, width, height,
resized }` (null for other files). Its `downloadUrl` works with the same
  `Authorization: Bearer bat_…` key.
- `add_reaction` / `remove_reaction` (`{ target, emoji }`; `target` is a task ref, an issue ref or a
  reply id) return `{ targetType, targetId, ref, url, reactions }`, where `ref` is the team-qualified
  task or issue (for a reply, the one it is on) and `url` the target's absolute URL.

### Projects (projects module)

Schemas: `shared/schemas/projects.ts`. `Project` = `ProjectSummary` + `{ readme, readmeSource, createdBy, keyAliases, statuses: Status[], labels: Label[], difficulties: Difficulty[] }`; difficulty levels (BAT-24) start as Easy / Normal / Hard, and tasks carry `difficulty: { id, name, color, position } | null` (`difficultyId` on create and update, `difficulty` by name in the MCP task tools). BAT-28: the difficulty belongs to the task _in a stage_ (`task_stage_difficulty`, like assignments); `task.difficulty` is its current stage's (a mirror kept in `task.difficulty_id`, so cards, filters and lists read it as before). The first visit to a stage takes the stage's `defaultDifficultyId`, else keeps the one it came with; a return restores the stage's last value; a move's `difficultyId` sets it for the stage it goes to (wins over both); a task created with `difficultyId` has it in its first stage (else that stage's default); `PATCH /api/tasks/:taskId { difficultyId }` changes the current stage's (with `statusId`, the new stage's). A difficulty changed by a move is audited as `task.updated` (`changes.difficulty` in names, `meta.stage`);
`ProjectSummary` = `{ id, teamId, teamSlug, name, key, ref, description, icon, color, counts: { tasks, assignedTasks, completedTasks, openTasks, doneTasks, openIssues, resolvedIssues }, path, createdAt, updatedAt }` (`assignedTasks`: someone is assigned in the task's current stage; `completedTasks`: in a stage that doesn't block its dependents; `openTasks` = `tasks - completedTasks` and `doneTasks` = `completedTasks` are kept for older clients);
`Status` = `{ id, projectId, pipelineId, name, color, icon: 'circle'|'dashed-circle'|'half-circle'|'dot-circle'|'check-circle'|'x-circle'|'pause-circle'|'square'|'triangle'|'diamond'|'star'|'flag', position, isDefault, taskCount, rules: StageRules, defaultDifficultyId: string | null }` (BAT-28: the difficulty of a task's first visit, a level of the project; audited as `changes.defaultDifficulty` by name) (statuses are stages: no open/done category since 2026-09-27; what a stage does is its `rules`, see Pipelines);

**Pipelines (BAT-25).** A project has one or more pipelines, each an ordered set of statuses (stages)
with its own board. Pipelines are mandatory: every project has a default pipeline (`isDefault`,
renamable, never deleted), created with the project (named by `pipelineName`, "Main" without one;
MCP `create_project` takes `pipeline`), and projects from before BAT-25 hold all their statuses in
one named "Default". `Pipeline` = `{ id, projectId, name, slug,
color, icon, position, isDefault, viewRule, createRule, manageRule, statusCount, taskCount,
openTaskCount, canCreateTasks, canManage }` (`openTaskCount`: its tasks not completed); `Project.pipelines` lists those the viewer can see and
`Project.statuses` only their stages. Status names, positions and the default status are per
pipeline. Who-rules (`PrincipalRule | null`): `viewRule` null = everyone in the project sees it and
its tasks (otherwise its tasks are hidden from the board, the list, task pages, search, My tasks and
`claim_next_task` for everyone else); `createRule` null = everyone with `CREATE_TASKS`;
`manageRule` null = only `MANAGE_STATUSES`, which sees and manages every pipeline. `GET
/api/projects/:projectId/statuses?pipeline=` lists one pipeline's stages; `POST …/statuses` takes
`pipelineId` (default: the default pipeline). Tasks: `POST …/tasks` takes `pipelineId` (starts in its
default status; the caller must be allowed to create tasks there), the board and list take
`?pipeline=<id>`, and `TaskCard.status.pipeline = { id, name, isDefault }`. Moving a task to a stage
of another pipeline needs the right to move it on from its stage (its move rule) and to create tasks
in the target; the source stage's criteria and approvals don't apply (owners and administrators can
force it). Pipeline changes emit `status.changed` and are audited on the project as
`pipeline.created|updated|deleted` and `project.pipelines_reordered`. Copying a pipeline
(`…/pipeline/copy[-preview]`) takes `fromPipelineId`/`pipelineId` (`fromPipeline`/`pipeline` in the
preview query), defaulting to the default pipelines, and may copy between pipelines of one project.
`Label` = `{ id, projectId, name, color, description, issueCount, taskCount }`. Counts ignore deleted
items. Reads need `VIEW_PROJECT` in the project (404 otherwise, as for non-members); writes need the
permission in the last column, in that project (see Project access below).

#### Project access (docs/design/agents-and-pipelines.md §3)

Schemas: `shared/schemas/projectAccess.ts`. Permissions are team-level (`ADMINISTRATOR`,
`MANAGE_TEAM`, `MANAGE_ROLES`, `MANAGE_MEMBERS`, `CREATE_INVITES`, `MANAGE_INVITES`,
`MANAGE_PROJECTS`, `VIEW_AUDIT_LOG`, `MANAGE_TRASH`: from team roles only) or project-level
(`VIEW_PROJECT`, `MANAGE_PROJECT_ACCESS`, `MANAGE_STATUSES`, `MANAGE_LABELS`, `CREATE_ISSUES`,
`CREATE_TASKS`, `REPLY`, `UPDATE_TASKS`, `RESOLVE_ISSUES`, `EDIT_ANY_CONTENT`, `DELETE_ANY_CONTENT`,
`MENTION_EVERYONE`: team roles give the default, overrides change it per project). Effective
project permissions: the project-level part of the member's team permissions → the `@everyone`
override (deny, then allow) → the overrides of their other team roles and their project roles (all
denies, then all allows) → their own override (deny, then allow). The owner and `ADMINISTRATOR`
bypass overrides; `MANAGE_PROJECTS` always keeps `VIEW_PROJECT`; agent members are capped by
their owner's permissions in the same project. **Without `VIEW_PROJECT` a project doesn't exist
for the user**: 404 on it and everything in it, left out of `GET /api/me`, project lists, search,
My tasks, the dashboard, the inbox and live events, and they get no notifications about it (the
team audit log stays complete for `VIEW_AUDIT_LOG`).

Reads need `VIEW_PROJECT`; writes need `MANAGE_PROJECT_ACCESS` in the project or the team's
`MANAGE_PROJECTS` (owners and admins always), plus anti-escalation without `ADMINISTRATOR`: an
override may only change (allow, reset or deny) permissions the actor has in the project, and a
project role can only be given, taken or deleted when the actor has every permission its override
mentions.

`ProjectRole` = `{ id, projectId, name, slug, color, position, members: [UserSummary & { isAgent }], createdAt, updatedAt }`;
`PermissionOverride` = `{ subjectType: 'team_role'|'project_role'|'user', subjectId, subjectName, subjectColor, allow: Permission[], deny: Permission[], updatedAt }`;
`ProjectPermissionsResponse` = `{ projectId, canManage, permissions (the viewer's), overrides: PermissionOverride[] }`.

#### Pipelines (docs/design/agents-and-pipelines.md §5)

Schemas: `shared/schemas/pipelines.ts`. Every `Status` carries `rules: StageRules` =
`{ instructions (markdown), handoff: { mode: 'keep'|'nobody'|'specific'|'pool'|'round_robin'|'least_busy'|'author'|'mover'|'stage_holder', rule?: PrincipalRule, statusId? }, notify: PrincipalRule|null, onEnter: { resolveIssues, releaseClaim, notifyAuthor, notifyAssignees, notifyPreviousHolder }, blocksDependents, claimable, allowCreate, exitCriteria: [{ id, text }], moveBy: { assignees, claimer }, moveRule: PrincipalRule|null, approvals: { count, rule: PrincipalRule, dismissOnChange }|null, autoAdvance, nextStatusId|null, sendBackTo: statusId[] }`
(the defaults, `keep`/`null`/all `false`/`true`/`true`/`[]`/`null`/`null`/`false`/`null`/`[]`, change nothing; a
status created without `sendBackTo` gets every earlier stage of its pipeline, and a new project's Done
can send back to Open). `sendBackTo` (BAT-27) lists the earlier stages of the same pipeline a task may
be sent back to (`400` for any other stage; ids of stages deleted or reordered after since are ignored,
and dropped when other rules are saved). The deprecated `allowSendBack` is still accepted in a patch:
`true` sets `sendBackTo` to every earlier stage, `false` empties it. Statuses have no hidden category: `onEnter.resolveIssues` resolves the issues the task `fixes`, `onEnter.releaseClaim` releases its claim, `onEnter.notifyAuthor` sends `task_done` ("Reached <stage>") to the author and `onEnter.notifyPreviousHolder` to whoever held it in the stage it left; `onEnter.notifyAssignees` (default true) sends `assigned` to the people the hand-off assigns; they run on every entry. A hand-off to `nobody` also releases the claim. `blocksDependents: false` means tasks there no longer block the tasks waiting on them and count as completed (`completedAt` is set on entry, kept while moving between such stages and cleared on entering a blocking one; changing the rule updates the stage's tasks). `claimable: false` keeps `claim_next_task` away and makes `claim_task` need `moveToStatusId`. `allowCreate` (BAT-34; off for a new stage, turned on by making a stage the default) lets new tasks start in the stage: `POST …/tasks` (and `…/tasks/from-issue`, MCP `create_task`) with a `statusId` whose stage doesn't allow it is `400`; without one the task starts in the pipeline's default stage when it allows it, else in the first stage that does, else `400` ("No stage of <pipeline> accepts new tasks…"). A new pipeline (and a new project's first one) gets five plain stages, Backlog (the default), To do, In progress, In review and Done, each able to send tasks back to every earlier one and otherwise with the defaults (no instructions, criteria, approvals or move rules, hand-off `keep`); Backlog and To do have `allowCreate`; Done has `handoff: nobody`, all the finishing `onEnter` flags, `blocksDependents: false` and `claimable: false`. A stage created without `rules` has the defaults, `allowCreate` off and `sendBackTo` every earlier stage. `copyRulesFrom` ("Create from existing") starts a new stage from the rules of any stage the caller can see (404 otherwise), in any project: everything but name, color, icon, position and the default flag; `rules`, `defaultDifficultyId` and `isDefault` apply on top. Stages it names (`nextStatusId`, `sendBackTo`, a `stage_holder` hand-off) map to this pipeline's stage of the same name (case-insensitive; the same stage within one pipeline), people and roles map like the pipeline copy (same user if a member, team and project roles by name), the default difficulty by level name; what has no match is dropped rather than blocking, a rule left naming nobody is cleared (a hand-off falls back to `keep`), and `copied.dropped` lists each ("@ann (approvers)"). MCP `create_status` takes `copyFrom` (a stage ref) and `copyFromProject`. `onEnter` in a patch merges flag by flag. `POST /api/projects/:projectId/statuses`
and `PATCH /api/statuses/:statusId` take `rules` (a partial `StageRules`: only the fields given change;
`MANAGE_STATUSES`); stages it names must be statuses of the project and principals members, roles and
project roles of its team (`400` otherwise). Rule changes are audited on `status.updated` in words
(`changes.approvals: { from: null, to: '1 from Reviewer (people)' }`, `nextStage`, …) and apply to
tasks the next time they move.

Assignments belong to a task and a stage: a task's assignees are the ones of its current status;
assigning and unassigning edit those, and the other stages' keep who held the task there (history).
A task entering a stage (created there, moved, status changed, claimed with `moveToStatusId`, sent
back, auto-advanced, or carried along when its status is deleted) gets the stage's hand-off, which
decides that stage's assignees (`task.handed_off` with `changes.assignees` when they differ from the
stage it left): `keep` restores the assignees it had in that stage on an earlier visit when there
were any (`meta.restored`), else copies the previous stage's; `nobody` assigns nobody; `specific`
assigns the rule's users, `pool` assigns nobody and stores the rule in the task's pool,
`round_robin` rotates through the rule's users by the stage's last round-robin pick, `least_busy`
picks the one directly assigned to the fewest tasks of the project (current stages), `author`,
`mover`, `stage_holder` the people and roles assigned to it in `statusId`; only members who can see
the project, and when nobody matches it behaves as `keep`; a hand-off releases a claim whose holder
no longer has the task, a pool always does; a task created with assignees keeps them, and assignees
given in the same `PATCH` as a new status become the new stage's (no hand-off),
`stage_entered` notifications for `notify`, and a new visit: coming back to a stage dismisses its
earlier approvals and archives its evidence (`task_stage_evidence.archived_at`), so its exit criteria
need new evidence; both stay as history.

Moves within a pipeline are strict (BAT-27), in every project, with or without rules:

- **Forward** only to the stage's next stage (`nextStatusId`, else the next column; the last stage has
  none). It needs the mover to be allowed to move it on (`moveBy`/`moveRule`; `403` naming who may),
  evidence for every exit criterion and `approvals.count` approvals with no open "changes requested"
  (`409` listing exactly what is missing, `details: { from, to, missing }`). Any other later stage is
  refused (`403` "From X, tasks only move on to Y"): a stage that should be skipped is configured out
  with `nextStatusId`.
- **Back** only to a stage of `sendBackTo` (`403` naming them otherwise, or "X doesn't send tasks
  back"), with a non-empty `reason` (`400` `validation_failed`, `details.field: 'reason'`). No approvals
  or evidence are needed. Who may: whoever may move it on (anyone who may move tasks when the stage
  names nobody), plus whoever may approve the stage — an approver needs no `UPDATE_TASKS` for a move
  back with `POST /move`. The reason is stored on the new visit (`task_stage_entry.return_reason`,
  `returned_by_id`, `returned_via_key_id`, `returned_from_status_id`), posted as a reply by the mover
  ("Sent back from Human Review: …"), audited on the move's row (`task.moved`, or `task.updated` for a
  `PATCH`) as `meta.direction: 'back'` and `meta.reason`, and given to the returned stage's agent
  jobs (`payload.returnReason`, `payload.returnedFrom`; its agent assignees get an `assigned` job even
  when the hand-off kept them). `keep` restores the assignees the stage had before.
- Moves to another pipeline (BAT-25) are unchanged.

The team owner and administrators may pass `force: true, reason` to `PATCH /api/tasks/:taskId` or
`POST /api/tasks/:taskId/move` to make any move past every rule (audited as `task.forced` with
`meta.reason` and `meta.bypassed`; a forced move back is a return with that reason). Both also take
`evidence: { [criterionId]: text }`, saved first (even when the move is then refused); without
anything else to change they only save it. A claim with `moveToStatusId` follows the same rules (it
carries no reason, so it can't move a task back). `POST /move` also takes `difficultyId` (BAT-28, a
level id or `null`) for the stage it moves to (`400` without a change of stage).

`Task.stage` (on the full task, for every task whose status exists) = `{ status: { id, name }, instructions,
criteria: [{ id, text, evidence: { text, user, via, updatedAt } | null }], approvals: { required,
approved, rule (in words), dismissOnChange, given: [{ id, user, via, decision, comment, createdAt }],
canApprove } | null, moveRule (in words) | null, next | null, sendBackTo (the nearest send-back stage)
| null, canMoveTo: { forward: { id, name, difficultyId, missing: string[] } | null, back: [{ id, name,
difficultyId }] } (`difficultyId`: what the move would give that stage by default, BAT-28),
returnReason: { reason, by, via, from, at } | null (while the current visit is a return), visits: [{

### Agent action requests (sign-off; docs/design/agents-and-pipelines.md §6)

Schemas: `shared/schemas/agentActions.ts`. While a team's `agentSignoff` is on (the default), a
destructive operation by an agent member (a request with an API key, REST or MCP) doesn't run: once
the agent's own permission checks pass, the server stores an `agent_action_request`, notifies the
agent's owner (notification type `agent_action_request`, always delivered whatever their
`agent_notifications` level) and answers `202 { pendingApproval: true, requestId, message }` (MCP:
the same object as a normal tool result). Asking again for the same action while it is pending
returns the same request. The actions (`AGENT_ACTIONS`): delete a task, issue, project, status or
label; delete a reply or attachment someone else wrote (the agent's and its owner's own need no
sign-off); delete a role; remove a member; revoke someone else's invite link; and the owner-only
`delete_team`, `restore_team` and `transfer_team_ownership`, which an owner's agent can only ask
for, whatever the setting (agents of other members are refused as before). A paused agent can't ask
(`423`).

Only the agent's owner decides, in the web app (through a key the actor is the agent: `403`).
Approving runs the action through its own service again, so every check is made again at that time:
as the agent, via the key it asked with, for most actions; as the owner for owner-only ones. The
outcome is `approved` (with `result`, what the action returned) or `failed` (with `error`
`{ code, message }`, e.g. the agent lost the permission or the target is gone). Pending requests
expire after 7 days (hourly job; an overdue request already reads as `expired`). Deciding or expiry
marks the owner's notification read. Each change sends the personal `agent_action.changed` event to
the owner.

`AgentActionRequest` = `{ id, team: { id, name, slug }, projectId, action, status, summary, url, agent,
owner, via, runsAsOwner, result, error, createdAt, expiresAt, decidedAt, decidedBy }`; `status` is
`pending`, `approved`, `denied`, `expired` or `failed`; `summary` reads like
"delete BAT-12 “Fix login”".
